# Authentication for the individual API

Status: Implemented for local development.

Signup verifies ownership of either a phone number or email before creating an active account. A password is optional at signup. Password and one-time-code login are separate routes; existing accounts are never overwritten by repeated signup. The current account model has one canonical verified contact. Adding another contact requires a future verification and linking workflow.

Use service-owned workflows, framework-independent domain policies, repository-owned PostgreSQL access, and provider ports. `AuthenticationRepositoryImpl` executes SQL, maps persistence records, and binds callbacks to one transaction connection directly; authentication SQL remains directly in its repository. Session identities use repository-owned Redis cache-aside with no database query on valid hits. Mutation triggers record targeted invalidation in a transactional outbox; post-commit delivery and periodic retries recover failures, while atomic Redis generations reject stale fills. This accepts a commit/delivery consistency window across replicas. Credentials, transactional reads and rate limits bypass cache. See [the cache protocol and its tradeoffs](../../src/modules/authentication/session-cache.md). Signup verification provisions an empty NGN wallet, so its runtime requires the wallet-ledger migration and wallet-provisioning privileges. Authentication remains separate from payment authorization. Database types come from the complete migration chain; each repository selects only the tables it owns.

Use Argon2id for passwords, keyed challenge digests for short codes, and opaque 256-bit bearer sessions with only token digests stored in PostgreSQL. Stateful sessions preserve authoritative revocation and account-disable enforcement. The first version used a 24-hour token. The [current session policy](../../src/modules/authentication/README.md) issues 15-minute access and rotating refresh proof with a fixed 30-day family deadline; consumed-proof reuse revokes the family. Read-only Redis hits retain their documented invalidation window, while protected writes and renewal use authoritative PostgreSQL. [Device authentication](0005-device-authentication.md) extends session issuance with signed device proof and enrollment requiring recent primary authentication, which refresh does not renew. JWT libraries already installed in the workspace are not required for these opaque sessions.

Codes expire after five minutes, permit five guesses, and are protected by contact and IP budgets. Failed attempts must commit, so services return unsuccessful transaction results before throwing public errors. A row lock and one transaction bind successful code consumption, account creation, the initial NGN wallet and both liability accounts, and session creation. `AuthenticationCodeService` chooses signup provisioning through repository contracts; `PostgresCodeRedemptionRepository` binds the existing feature repositories to one connection. This focused transaction boundary avoids feature-module cycles and duplicate ledger SQL. Wallet or session persistence failure rolls back the account and preserves the signup proof for retry until expiry. Login and recovery do not provision wallets or backfill older accounts.

The user selected local delivery. Mailpit captures both email and simulated SMS behind a delivery interface. This adapter is restricted to loopback and cannot run in production. It uses bounded synchronous delivery: a crash after sending but before acceptance is recorded requires a new challenge. Real delivery, compromised-password screening, lost-contact recovery, password-change notifications, stronger payment authorization, and expired-data cleanup must be completed before a production release.

The password length policy, generic failures, and throttling draw on [OWASP authentication guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html). The Argon2id parameters follow [OWASP password storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Codes and sessions are application access mechanisms, not a claim of MFA or financial identity verification.

[Password recovery](../../src/modules/authentication/password-recovery.md) now reuses purpose-bound codes and the existing local delivery. Successful reset atomically replaces the password and revokes account sessions/device keys. Credential versions reject older proofs and in-flight logins.
